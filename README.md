# PX4 ROS 2 Offboard Control Node for Exploration and AruCo detection

[![OpenCV](https://img.shields.io/badge/OpenCV-5C3EE8?style=flat&logo=opencv&logoColor=white)](https://opencv.org/)

This project is an implementation of an Offboard Control ROS 2 Node for the PX4 controller that autonomously pilots the drone along a pre-determined path read from a JSON file until the vision sensor on the vehicle identifies a certain ArUco marker (in the current implementation the marker with id=0), at which point the drone terminates the exploration phase and performs a controlled descent on the marker. 

https://github.com/user-attachments/assets/89a325f9-a58e-4877-ae81-f5c0a80ea774

# Dependencies
The project is built using the standard ROS 2 client library (`rclcpp`, `sensor_msgs`), OpenCV (`opencv2`, with the `aruco` module, and `cv_bridge`), `nlohmann_json`, (`behaviortree_cpp`) and the PX4 message definitions (`px4_msgs`) for C++. 

# ArUco Detection

<img width="2720" height="1080" alt="aruco_detection_pipeline" src="https://github.com/user-attachments/assets/f5b1a887-12e6-45fc-a4c0-faa784f0024a" />

The function `cameraCallback` (called whenever a new image is published on the `/camera/image_raw` topic) receives a `sensor_msgs::msg::Image`. This data is turned into a `cv::Mat` in single intensity channel as ArUco detection works with single intensity. 
The function `cv::aruco::detectMarkers` thresholds the image, finds square-looking contours, warps each candidate to a canonical square and reads its bit pattern. It then compares that pattern with the dictionary (`DICT_4X4_50`, a 4×4 grid with 50 valid IDs). The main output of this operation is the id of the marker that has been detected. After this, if the resulting id is equal to the desired id, the node extracts the marker's coordinates using the detected pixel `corners[i]` and  the camera intrinsics: `fx = fy = 539.94`, `cx = 640`, `cy = 480`, zero distortion.
Those intrinsics describe a 1280×960 image, which gives a field of view of about 100° horizontally and 83° vertically. At 5 m altitude the camera sees a ground patch of about 11.9 × 8.9 m, and the 1 m marker is about 108 px wide. The result `tvec` is the marker centre in the camera frame, in metres: x to the right of the image, y down the image, z along the optical axis. For a downward camera, z is roughly the height above the marker. `tvec` is in metres only if the real marker is 1 m wide. If the Gazebo model is a different size, then the node must be modified to take account of this difference. Each detection produces an absolute target in PX4’s local frame. As the drone approaches, the offset shrinks and the target settles, so this is closed-loop visual servoing.

# Descent on target
Once the marker is found for the first time, the drone keeps its altitude and starts moving over the marker. From this moment `publish_trajectory_setpoint` stops following the JSON checkpoints, and the 10 Hz timer sends `coords` instead.
For later detections each frame blends the new target into the old one with an exponential moving average:

`coords = 0.8 * coords + 0.2 * target`

This only smooths noise in the x/y estimate. From the second detection the z coordinate is set to 0 so the drone descends on the target while continuing horizontal and vertical alignment, until the vehicle lands.

### Execution Example
 
To run the offboard node and make it follow the checkpoints stored in a JSON file (generated by the pathfinding script):
```bash
source /opt/ros/jazzy/setup.bash
source ~/ros2_jazzy/install/setup.bash
 
ros2 run precision_landing precision_landing_node \
    --ros-args -p checkpoints_file:=/home/user/checkpoints.json
```
 
# Node Launch Guide
 
This guide describes how to start the `precision_landing_node` and which parameter it needs.
 
---
 
## Prerequisites
 
Before launching the node, make sure the following are running:
 
1. The PX4 SITL simulation (Gazebo world with the drone model).
2. The Micro XRCE-DDS agent, so the `/fmu/...` topics are visible in ROS 2.
3. The camera bridge publishing images on `/camera/image_raw`.
4. The package is built and both setup files are sourced in the terminal you use.
---
 
## Node Parameters
 
| Argument | Type | Default | Description |
| :--- | :--- | :--- | :--- |
| `checkpoints_file` | `string` | `checkpoints.json` | Path to the JSON file with the checkpoints. A relative path is resolved from the directory where you launch the node, so an **absolute path** is recommended. |
 
Parameters are passed with `--ros-args -p name:=value`.
 
---
 
## Topics
 
| Direction | Topic | Description |
| :--- | :--- | :--- |
| Subscribes | `/camera/image_raw` | Camera frames used for ArUco marker detection. |
| Subscribes | `/fmu/out/vehicle_local_position_v1` | Drone position in the local NED frame. |
| Publishes | `/fmu/in/offboard_control_mode` | Offboard heartbeat (10 Hz). |
| Publishes | `/fmu/in/trajectory_setpoint` | Position setpoint (10 Hz). |
| Publishes | `/fmu/in/vehicle_command` | Arm and offboard mode commands. |
 
---
 
## JSON File Format
 
```json
{
    "checkpoints": {
        "S": {"x": 0.0, "y": 0.0, "z": -5.0},
        "A": {"x": 5.0, "y": 0.0, "z": -5.0},
        "B": {"x": 10.0, "y": 2.0, "z": -5.0}
    }
}
```
- Coordinates are in meters in the PX4 local **NED** frame: `x` = north, `y` = east, `z` = down (so `-5.0` means 5 m above the takeoff point).
- Checkpoints are visited **in the order they appear in the file**. The `edges` field is not used by the node.
- The first checkpoint is also a waypoint: if it is not at the takeoff point, the drone flies there in a straight line.
